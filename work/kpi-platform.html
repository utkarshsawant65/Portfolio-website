production · private code kpi platform

One source of truth for the founders' weekly review

An internal web app on a Postgres star schema: Django UI, role-based access and a Power BI layer, built in about two months with one teammate.

Role
data engineer · Timeline: 2025 · Team: 2
Stack
Django · PostgreSQL · Power BI · Notion API · GCP VM
Code
private (company IP). Walkthrough on request: email me

01Problem

Team performance and plan tracking was spread across spreadsheets and ad-hoc reports. The founders ran weekly and monthly reviews without one agreed place for the numbers, so each meeting started with reconciling what was current.

The goal was a single source of truth the whole team could feed and the founders could trust.

02Constraints

  • Two people and roughly two months, from requirements to deployment.
  • Three inbound channels: scheduled Notion API pulls, Google Sheets, and direct UI input.
  • Three roles with different rights: user, admin and founder.
  • Small infrastructure: one VM, no platform team.

03Architecture

04Key decisions

  • A star schema built for rollups. One KPI fact table with date, organisation, objective and user dimensions makes weekly and quarterly views cheap queries.
  • Power BI first, Django second. Reporting started in Power BI on the Postgres layer and moved into a Django app once the team needed auth, RBAC and a better input experience.
  • Three roles, enforced in the app. User, admin and founder roles, a forgot-password flow and logging, so access is a property of the system and not of who holds the link.

05Data model · Schema

fct_kpi        key_result · value · period
 ├─ dim_date        day · month · quarter
 ├─ dim_org         team · level
 ├─ dim_objective   id · name · target
 └─ dim_user        role: user | admin | founder

06Results

10–12active users
48metrics under one data contract
~2 mofrom requirements to deployment

Founders use it as the single source of truth in weekly and monthly review meetings.

07What I'd do next

  • Automated freshness checks on the Notion pulls, so a stalled sync is flagged before the meeting and not during it.
  • Move the Power BI semantic layer fully onto the same star schema, so the app and the reports share one set of definitions.
